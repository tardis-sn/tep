# TEP016: Composable, Numba-safe transport physics

## Summary

Replace the classic, IIP, and nonhomologous transport solver stacks with one
`MCTransportSolver`. Each workflow will construct an explicit Python
`TransportPhysics` object inside its initializer and pass that object to the
solver. There will be no `auto` mode, workflow-type inference, or aggregate
kernel constants.

This refactor depends on the existing virtual-packet relocation work rather
than reimplementing it here.

Example workflow initialization:

```python
class SimpleTARDISWorkflow:
    def __init__(self, configuration, packet_source=None):
        physics = TransportPhysics(
            kinematics=Kinematics.HOMOLOGOUS,
            relativity=Relativity.FULL,
            line_interaction=LineInteraction.MACROATOM,
            electron_scattering=True,
            continuum_processes=True,
        )
        self.transport_solver = MCTransportSolver.from_config(
            configuration, packet_source=packet_source, physics=physics
        )
```

## Description

### Problem and motivation

Transport physics is currently spread across classic, IIP, and nonhomologous
solver modes. Physics selection is also represented in multiple places,
including workflow or geometry inference, YAML configuration, mutable global
process flags, and mode-specific Numba state. This makes combinations
difficult to reason about, causes duplicated implementations, and risks
letting different parts of a run use different physics selections.

The proposal composes the independent choices explicitly:

```text
TransportPhysics
├── kinematics: homologous | nonhomologous
├── relativity: partial | full
├── line_interaction: none | scatter | downbranch | macroatom
├── electron_scattering: bool
└── continuum_processes: bool
```

The resolver will validate the selected combination before JIT compilation,
while the compiled transport path will receive only Numba-safe state. This
should reduce duplicated transport code, make unsupported combinations fail
early, and preserve the existing random-draw order and scientific behavior for
supported combinations.

### Goals

- Provide one `MCTransportSolver` for the supported classic, IIP, and
  nonhomologous workflows.
- Make every workflow construct an explicit `TransportPhysics` object.
- Separate kinematics, relativity, line interaction, electron scattering, and
  continuum-process selection.
- Use one shared real-packet propagator and packet event-state handler.
- Preserve packet seeding, output sign conventions, estimator behavior,
  tracker behavior, and existing nonhomologous approximations for supported
  combinations.
- Validate unsupported combinations before Numba compilation.
- Remove mutable global process flags and mode-specific duplicate opacity
  state.
- Keep the compiled boundary Numba-safe and assert nopython compilation for
  every supported combination.

### Non-goals and assumptions

- Gamma-ray transport and formal-integral physics remain outside this
  refactor.
- Virtual-spectrum relocation is supplied by PR #3738 and the
  `vpackets-spectrum-solver` follow-on branch, not this refactor.

### User-facing configuration changes

Transport-physics selection will move out of YAML and into explicit workflow
construction. These settings will become legacy configuration schemas and examples:

- `enable_full_relativity`
- `enable_nonhomologous_expansion`
- `line_interaction_type`
- the two scattering-disable flags

Continuum species remain material/plasma data; `continuum_processes` controls
whether transport uses them. The explicit physics object must also configure
the packet source, spectrum and formal-integral compatibility validation,
opacity and macro-atom assembly, and Numba run configuration.

## Implementation

### Host-side physics specification and resolver

Add `tardis/transport/montecarlo/physics.py`:

```python
from dataclasses import dataclass
from enum import StrEnum


class Kinematics(StrEnum):
    """Velocity field and line-resonance-distance treatment."""

    HOMOLOGOUS = "homologous"
    NONHOMOLOGOUS = "nonhomologous"


class Relativity(StrEnum):
    """Frame transformation used for packet propagation."""

    PARTIAL = "partial"
    FULL = "full"


class LineInteraction(StrEnum):
    """Bound-bound process enabled in packet transport."""

    NONE = "none"
    SCATTER = "scatter"
    DOWNBRANCH = "downbranch"
    MACROATOM = "macroatom"


@dataclass(frozen=True, slots=True)
class TransportPhysics:
    kinematics: Kinematics
    relativity: Relativity
    line_interaction: LineInteraction
    electron_scattering: bool
    continuum_processes: bool
```

`Kinematics` selects only the velocity/resonance implementation; it does not
imply a process set. `Relativity` selects only the frame treatment.
`LineInteraction.NONE` disables bound-bound events, while the other values
select their existing redistribution treatment. The resolver combines these
independent objects with electron and continuum choices, then rejects only
unsupported combinations before Numba compilation.

The resolver interface is:

```text
resolve_transport_kernel(physics, geometry, opacity_state)
    -> ResolvedTransportKernel
```

`ResolvedTransportKernel` is a host-only dataclass containing a matched
`driver` and `packet_propagator` Numba dispatcher plus a
`NumbaTransportPhysics` jitclass. The dataclass never crosses the Numba
boundary. The host calls the concrete driver as:

```text
driver(
    packet_collection,
    geometry,
    opacity_state,
    numba_physics,
    trackers,
    show_progress_bars,
    packet_propagator,
)
```

Numba specializes the driver on the concrete propagator type.
`packet_propagator` receives the same jitclass, bulk/line/continuum
estimators, and tracker, and chooses only its resolved kinematics
implementation. No Python registry, callable, or dataclass enters `prange`.

`NumbaTransportPhysics` is an `@numba.experimental.jitclass` with exactly four
scalar fields:

- `relativity_code: int64`
- `line_interaction_code: int64`
- `electron_scattering_enabled: boolean`
- `continuum_processes_enabled: boolean`

It owns no arrays and exposes no Python methods. `propagate_packet` branches on
its integer and boolean fields only after the kinematic propagator has been
selected. Process functions take explicit packet, opacity-state, estimator,
and local-velocity arguments. Packet seeds remain in `PacketCollection`;
tracking allocation and all virtual-packet settings remain host-side. This
removes the current mutable global process flags without introducing a second
source of physics truth.

### Capability matrix

The capability matrix is the Cartesian product of the 64
`TransportPhysics` tuples. Initially support exactly these 26 tuples:

- homologous/partial or homologous/full with continuum disabled: all four
  line choices and both electron-scattering choices;
- homologous/full/macroatom with continuum enabled: both
  electron-scattering choices;
- nonhomologous/partial with continuum disabled: all four line choices and
  both electron-scattering choices.

Every other well-typed tuple raises `NotImplementedError` before JIT.
Malformed component values raise `TypeError`.

Initially reject:

- full relativity with nonhomologous kinematics;
- continuum with nonhomologous kinematics or partial relativity;
- continuum without macroatom line handling.

Preserve current nonhomologous approximations exactly.

### Module layout

Separate compiled calculations by concern:

```text
montecarlo/
├── kernels/
│   ├── driver.py          # one real-packet parallel loop
│   ├── kinematics.py      # homologous and nonhomologous resonance/frame kernels
│   └── processes.py       # line, electron, and continuum event kernels
├── physics.py             # Python composition, resolution, validation
└── solver.py              # one solver and tracker lifecycle
```

Keep two kinematic/resonance implementations, but share packet movement,
estimator accumulation, tracking, process dispatch, and result attachment.
Numba should specialize the generic driver for the resolved compiled callbacks
and assert nopython compilation for every supported combination.

### Solver and workflow migration

Make `physics: TransportPhysics` a required keyword-only argument of
`MCTransportSolver.from_config` and all direct `MCTransportSolver`
construction. `SimpleTARDISWorkflow`, `TypeIIPWorkflow`, and
`NonhomologousTARDISWorkflow` must each construct their explicit
`TransportPhysics` object inside `__init__` and pass that local object to every
solver they create.

`Simulation.from_config` should construct the selected workflow without
accepting a second, external physics object. Workflows may validate that their
explicitly constructed geometry and plasma data are compatible, but must not
derive `Kinematics` through class-name or `isinstance` inference.

Construct the relativistic or nonrelativistic packet source from
`physics.relativity`, and pass the same selection to spectrum and formal-
integral compatibility validation.

### Opacity and process state

Unify the Numba opacity state and eliminate mutable continuum globals:

- `NONE` builds no bound-bound macro-atom state and supplies zero line opacity.
- `SCATTER` uses the scattering opacity path.
- `DOWNBRANCH` and `MACROATOM` build their existing bound-bound macro-atom
  states.
- `electron_scattering=False` supplies explicit zero electron opacity and
  never mutates `SIGMA_THOMSON`.
- A supported continuum selection uses `ContinuumMacroAtomSolver` plus
  continuum estimator allocation.
- Disabled processes use explicit zero-length or zero-valued state data, not
  global flags.

### Virtual-packet dependency

Virtual-packet relocation is out of scope. Integrate the tracker contract and
transport-loop removal from [PR #3738](https://github.com/tardis-sn/tardis/pull/3738),
(`vpackets-post-process`, `ece8d4ff`) and its follow-on
`vpackets-spectrum-solver` branch (`3ed35012`) as a dependency.

This refactor must neither recreate their spectrum post-processing
implementation nor change its replay, RNG, logging, or tracker-lifetime
semantics. Resolve merge conflicts only where the unified transport kernel
changes the tracker interface, and retain their tests as compatibility
coverage.

Until that work adds continuum replay, reject
`continuum_processes=True` with requested virtual packets before transport
setup.

## Backward compatibility

This is intended to preserve scientific behavior and user-visible output for
the supported physics combinations, including current random-draw order,
packet seeding, estimator behavior, tracker behavior, and existing
nonhomologous approximations.

However, the proposal intentionally introduces user-facing and internal
incompatibilities:

- `MCTransportSolverClassic`, `MCTransportSolverIIP`, and
  `MCTransportSolverNonhomologous` are replaced by `MCTransportSolver`.
- Mode-specific `run_*` methods are replaced by shared `initialize_transport_state`,
  `run`, and `from_config` methods.
- `physics: TransportPhysics` becomes a required keyword-only solver argument.
- Workflows must construct physics explicitly and may not infer kinematics
  from workflow type, class name, geometry, YAML, or mutable global state.
- `OpacityStateNumbaIIP` and `MonteCarloTransportStateNonhomologous` are
  removed after migration to unified state types.
- Unsupported combinations fail early with `NotImplementedError`; malformed
  component values fail with `TypeError`.
- Continuum-enabled virtual-packet requests are rejected until compatible
  continuum replay is available in the dependency branch.

## Alternatives

The following alternatives are possible:

- **Retain separate solver stacks:** rejected in favor of one shared solver to
  remove duplicated drivers, state types, and process implementations.
- **Infer physics from workflow type, geometry, or YAML:** rejected in favor of
  an explicit `TransportPhysics` object constructed by each workflow.
- **Use an `auto` mode or aggregate kernel constants:** rejected in favor of
  independent, typed component selections and a validated capability matrix.
- **Pass Python registries, callables, or dataclasses into `prange`:** rejected
  because the compiled boundary must remain Numba-safe.
- **Keep mutable global process flags:** rejected in favor of explicit zero
  opacity/state data and the four-field `NumbaTransportPhysics` jitclass.
- **Move virtual-packet behavior as part of this refactor:** rejected in favor
  of depending on PR #3738 and its follow-on branch, preserving their replay,
  RNG, logging, and tracker-lifetime ownership.
- **Generalize the nonhomologous approximation:** rejected; the proposal
  retains the current approximation and requires separate paper-derived
  validation before extending it.

Concerns requiring discussion include the size of the migration, the risk of 
subtle numerical or random-stream changes, the maintenance burden of a 
26-combination capability matrix, and the need to coordinate dependent 
virtual-packet work.
